# Project context for Claude Code

The app is **Reachoreo** (renamed 2026-11-10; the Python package stays `reachy_dance`). GitHub: mathbecsan/Reachoreo.

## What this is
*Encendido*: a 76-second dance for two Reachy Mini robots and one human dancer (Mathias), filmed in the
Stanford Robotics Center kitchen mockup. Reachy A sits on the counter on the CAMERA'S LEFT, Reachy B on the
camera's right, the dancer in the middle. Story: everyone starts powered off (dancer frozen like a deactivated
humanoid, hood up), the robots wake first, charge him back to life, and all three end dancing at full power.
19 phrases of 8 counts at 120 BPM, in four acts (Off, The reboot, The spark, Switched on).

The score was designed in an animated web preview first; `tests/golden/encendido_robots.json` is that
preview's exact robot motion, and `choreography/encendido.py` must keep matching it.

## Architecture (see README.md for the diagram)
- One repo, organized by layer. Left/right is `--side A|B`, never separate code.
- `conductor.py` owns the show clock (show time 0 = first downbeat), plays music, prompts the dancer.
- `agent.py` runs once per robot: score + reactions + safety, streamed with `set_target()` at 50 Hz.
- `reactive.py` layers reactions on the score; the score always carries the show if perception fails.
- `perception/` publishes dancer state and cue events; `fake_dancer.py` stands in for rehearsal.
- Processes talk over ZeroMQ PUB/SUB (ports in `config/show.yaml`), JSON payloads, topics
  `clock`, `dancer`, `robot.A`, `robot.B`.

## Conventions
- Pose units match the preview (documented in `pose.py`); convert to SDK units only in `to_sdk()`.
- Never call blocking `goto_target()` inside the control loop; only for getting into position and resting.
- Keep SDK limits: pitch/roll under 35°, body under 155°, head minus body under 60°.
- Trigger counts in `encendido.yaml` are 0-based; on-page counts are 1-based.
- Run `pytest` after every change. All 85 tests must pass.
- Verified on the real robots (2026-11-10, two Lites over USB): movement sign conventions in show.yaml's
  calibration section are correct. Per-robot latency measured with tools/measure_arrival.py (B needs ~40 ms more than A; set 2026-11-10), not yet confirmed by a clap test;
  also unverified: and camera cue thresholds. Pin `reachy-mini` to the version on both robots
  (version mismatches have caused trouble before).

## Dances from songs and the site (built 2026-11-10)
Pages: `/` home.html (launcher + library), `/create` create.html, `/perform` perform.html, `/control` index.html; shared
top bar `static/nav.mjs`. A song dance is `library/<slug>/choreo.json`: phrases of {src: Encendido phrase 0-18, mirror},
played at `count_bpm` by `choreography/library.py` `GeneratedScore` (same interface as the encendido module, so agents,
reactor and monitor are unchanged); `config.load_choreography(slug)` picks it up. The conductor's `load <slug>` switches
dances; its clock message carries `choreo`, agents reload when idle and publish `choreo` in their status. The browser
plays the song (`static/songsync.mjs`), not the conductor. Song dances store `counts` (show time of every count, from the beat tracker); scores expose `count_of(t)` / `time_of(c)`: use them, never `t / BEAT`. Dances play as 4-count pieces (`halves` per phrase, `pieces_of`/`joint` in library.py, crossfade XF_BEFORE/XF_AFTER); the selector uses `move_profiles.json`, regenerated by `node tools/build_move_profiles.mjs` after preview edits. Phrases with `learned: true` play stored tracks from `choreo.learned.phrases[i]` (H/A/B arrays, `steps` per count; made by `static/learn.mjs`). JS twin of the mapping: `static/choreo.mjs` (tested against
Python in tests/test_library.py). Beat finding: `static/music.mjs` (tests/test_music_js.py). Launcher: `dashboard/launcher.py`.

## Setup wizard (`/setup`, built 2026-11-10)
`dashboard/setup.py` edits show.yaml line by line (`write_key`, comments kept); agents listen on the dashboard port for
`setup` (test moves) and `tune` (latency_s, calibration) messages. Calibration has `ant_swap` for robots whose antenna
wiring is mirrored.

## Control dashboard (built: `python -m reachy_dance.dashboard`, http://localhost:8080)
`dashboard/monitor.py` holds the checks (pure, tested in `tests/test_dashboard.py`); `server.py` is stdlib HTTP +
server-sent events; the conductor takes the dashboard's commands on the `cmd` topic (port `bus.dashboard`).
Agents publish `pose` (commanded) and `score` (pure score) lists in POSE_KEYS order in their status, plus
`cmd` (sent) and `meas` (measured by the daemon) in SDK units, 25 times a second.
The preview lives in `preview/encendido-preview.html`; `tools/build_stage_js.py` generates `static/encendido-stage.mjs`
from it (motion + drawings) for the rehearsal page. Never edit the .mjs by hand.
Rehearsal view (`/perform`, `static/perform.html`, math in `static/rehearsal.mjs`): browser camera + MediaPipe → POST /api/landmarks → `CameraBridge`
(server.py) → FeatureTracker(framing="upper") → publishes `dancer`. Scoring lives in `dashboard/sync.py`.
The reactor resets on each new run and accepts cues up to a quarter beat early (also across a phrase start).
`perception/pose_tracker.py` still uses MediaPipe's legacy `mp.solutions` API, removed in mediapipe 1.x.
Original brief: a local web page, served by a small Python process that joins the existing bus, to run and debug the show:
- Start / pause / resume / stop, start from any phrase, show clock and current phrase and count.
- Live status of each robot: connected, state, clock drift, last reactions, commanded pose vs score pose.
- Inconsistency checks between the two robots: phrase mismatch, drift between A and B beyond a threshold,
  a robot not publishing, a reaction fired on one side only when the phrase expects both.
- Dancer panel: seen / not seen, position on a stage strip, energy, recent cue events.
- A timeline of the 19 phrases with dancer cues, and an event log that can be exported for analysis.
The conductor should stay the single source of truth for the clock; the dashboard sends it commands.
